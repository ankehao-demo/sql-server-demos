# Data Migration Issues and Resolutions

This document describes common issues encountered during the SQL Server to PostgreSQL data migration and their resolutions.

## Data Type Conversion Issues

### Issue 1: Geography Data Type Coordinate Order

**Problem:** SQL Server geography type uses (latitude, longitude) coordinate order, while PostGIS uses (longitude, latitude).

**Resolution:** The transformation script (`02-transform/transform_data.py`) includes a `convert_geography()` function that swaps coordinate pairs when converting WKT representations.

**Example:**
```python
# SQL Server: POINT (47.6062 -122.3321)  # (lat, lon)
# PostGIS:    SRID=4326;POINT(-122.3321 47.6062)  # (lon, lat)
```

### Issue 2: Binary Data Encoding

**Problem:** SQL Server `varbinary` data cannot be directly exported to CSV without encoding.

**Resolution:** Binary data is base64-encoded during extraction and converted to PostgreSQL `bytea` hex format during transformation.

**Example:**
```python
# Extraction: binary -> base64 string
# Transformation: base64 -> \x hex format for PostgreSQL
```

### Issue 3: DateTime Precision

**Problem:** SQL Server `datetime2` supports up to 7 decimal places (100 nanoseconds), while PostgreSQL `timestamp` supports 6 decimal places (microseconds).

**Resolution:** The transformation script truncates nanosecond precision to microseconds. This is acceptable for most business applications.

### Issue 4: Computed Columns

**Problem:** Some SQL Server computed columns use functions that are not directly portable to PostgreSQL.

**Resolution:** 
- Simple computed columns are converted to PostgreSQL `GENERATED ALWAYS AS ... STORED` columns
- Complex computed columns (e.g., JSON extraction) are implemented as views
- Computed columns are excluded from data extraction and regenerated by PostgreSQL

**Affected Tables:**
- `application.people.searchname` - Generated column
- `warehouse.stockitems.searchdetails` - Generated column
- `sales.customertransactions.isfinalized` - Generated column
- `purchasing.suppliertransactions.isfinalized` - Generated column

## Temporal Table Migration

### Issue 5: System-Versioned Temporal Tables

**Problem:** SQL Server system-versioned temporal tables have automatic history tracking that PostgreSQL doesn't natively support.

**Resolution:** 
- Main tables retain `validfrom` and `validto` columns
- Archive tables (e.g., `tablename_archive`) store historical data
- Triggers maintain temporal behavior in PostgreSQL
- Both current and historical data are migrated

**Migration Steps:**
1. Extract data from main table
2. Extract data from archive table (if exists)
3. Load main table data (triggers disabled)
4. Load archive table data
5. Re-enable triggers

### Issue 6: Archive Table Column Differences

**Problem:** Archive tables in SQL Server may have slightly different column definitions (e.g., no computed columns).

**Resolution:** Archive tables are created with matching column structures, excluding computed columns that are regenerated.

## Foreign Key and Constraint Issues

### Issue 7: Circular Foreign Key Dependencies

**Problem:** Some tables have circular foreign key references that prevent straightforward loading.

**Resolution:** 
1. Foreign keys are disabled during data loading
2. Data is loaded in dependency order where possible
3. Foreign keys are re-enabled after all data is loaded
4. Validation script checks for orphaned records

### Issue 8: Self-Referencing Foreign Keys

**Problem:** Tables like `sales.customers` have self-referencing foreign keys (`billtocustomerid` references `customerid`).

**Resolution:** 
- Load all rows first with constraints disabled
- Enable constraints after all data is loaded
- Validation verifies referential integrity

## Sequence and Identity Issues

### Issue 9: Sequence Value Synchronization

**Problem:** After loading data, PostgreSQL sequences may not be synchronized with the maximum ID values in tables.

**Resolution:** The loading scripts include a `reset_sequence()` function that:
1. Finds the maximum value in the table
2. Sets the sequence to that value + 1
3. Handles shared sequences (e.g., `transactionid` used by multiple tables)

**Example:**
```sql
SELECT setval('sequences.customerid', 
              (SELECT MAX(customerid) FROM sales.customers), 
              true);
```

### Issue 10: Shared Transaction Sequence

**Problem:** SQL Server uses a single sequence for multiple transaction tables (`CustomerTransactions`, `SupplierTransactions`, `StockItemTransactions`).

**Resolution:** The sequence reset logic finds the maximum value across all tables sharing the sequence:
```python
OLTP_SEQUENCES = {
    'sequences.transactionid': [
        ('sales.customertransactions', 'customertransactionid'),
        ('purchasing.suppliertransactions', 'suppliertransactionid'),
        ('warehouse.stockitemtransactions', 'stockitemtransactionid'),
    ],
}
```

## Performance Issues

### Issue 11: Large Table Loading Performance

**Problem:** Loading large tables (millions of rows) can be slow with row-by-row inserts.

**Resolution:** 
- Use PostgreSQL `COPY` command for bulk loading
- Disable triggers during load
- Process data in batches (default: 10,000 rows)
- Use `UNLOGGED` tables for staging (OLAP)

### Issue 12: Index Maintenance During Load

**Problem:** Maintaining indexes during bulk loading significantly slows down the process.

**Resolution:** 
- Indexes are created after initial schema migration
- Consider dropping and recreating indexes for very large migrations
- Use `CONCURRENTLY` option for index creation in production

## Data Validation Issues

### Issue 13: Row Count Mismatches

**Problem:** Row counts may differ between source and target due to various reasons.

**Possible Causes:**
1. Data changes during migration (source is live)
2. Constraint violations filtering out rows
3. Encoding issues causing row parsing failures

**Resolution:** 
- Use consistent snapshots when possible
- Review validation logs for specific discrepancies
- Check constraint violation logs

### Issue 14: Character Encoding Issues

**Problem:** Special characters may not transfer correctly between SQL Server and PostgreSQL.

**Resolution:** 
- All CSV files use UTF-8 encoding
- SQL Server `nvarchar` maps to PostgreSQL `varchar` (both support Unicode)
- Extraction scripts explicitly set UTF-8 encoding

## Memory-Optimized Table Migration

### Issue 15: Memory-Optimized Tables

**Problem:** SQL Server memory-optimized tables (`ColdRoomTemperatures`, `VehicleTemperatures`) have special characteristics not available in PostgreSQL.

**Resolution:** 
- Converted to regular PostgreSQL tables
- `BIGSERIAL` used for identity columns
- Performance may differ; consider using `UNLOGGED` tables for similar use cases

## JSON Data Migration

### Issue 16: JSON Column Handling

**Problem:** SQL Server stores JSON as `nvarchar` with JSON functions, while PostgreSQL has native `jsonb` type.

**Resolution:** 
- JSON columns are validated during transformation
- Invalid JSON is logged and set to NULL
- PostgreSQL `jsonb` type provides better query performance

**Affected Columns:**
- `warehouse.stockitems.tags`
- `sales.invoices.returneddeliverydata`

## Troubleshooting Guide

### Connection Issues

**SQL Server Connection Failed:**
```
Error: pyodbc.Error: ('01000', "[01000] [unixODBC][Driver Manager]Can't open lib...")
```
**Solution:** Install ODBC Driver 18 for SQL Server:
```bash
curl https://packages.microsoft.com/keys/microsoft.asc | apt-key add -
curl https://packages.microsoft.com/config/ubuntu/$(lsb_release -rs)/prod.list > /etc/apt/sources.list.d/mssql-release.list
apt-get update
ACCEPT_EULA=Y apt-get install -y msodbcsql18
```

**PostgreSQL Connection Failed:**
```
Error: psycopg2.OperationalError: could not connect to server
```
**Solution:** Verify PostgreSQL is running and credentials are correct in `config.py`.

### Data Loading Errors

**Foreign Key Violation:**
```
Error: psycopg2.errors.ForeignKeyViolation: insert or update on table "x" violates foreign key constraint
```
**Solution:** Ensure tables are loaded in dependency order. Check for orphaned records in source data.

**Unique Constraint Violation:**
```
Error: psycopg2.errors.UniqueViolation: duplicate key value violates unique constraint
```
**Solution:** Check for duplicate data in source. May indicate table was not truncated before load.

### Validation Errors

**Sequence Not Synchronized:**
```
Warning: Sequence 'sequences.customerid' value (100) is less than max table value (500)
```
**Solution:** Run sequence reset:
```sql
SELECT setval('sequences.customerid', (SELECT MAX(customerid) FROM sales.customers), true);
```

## Best Practices

1. **Always run validation after migration** - Use `python run_migration.py --validate`

2. **Test with subset first** - Modify extraction scripts to add `TOP 1000` or `LIMIT 1000` for testing

3. **Monitor disk space** - CSV files can be large; ensure sufficient space in DATA_DIR

4. **Keep logs** - All scripts log to LOGS_DIR; review for issues

5. **Backup before migration** - Always backup PostgreSQL database before running load scripts

6. **Run ANALYZE after load** - Update PostgreSQL statistics:
   ```sql
   ANALYZE;
   ```

7. **Check for blocking queries** - Large loads may block other operations

8. **Use transactions wisely** - Batch commits prevent excessive WAL growth
